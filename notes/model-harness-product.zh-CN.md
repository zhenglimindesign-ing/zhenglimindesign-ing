# Model + Harness + Product：一个 AI 产品真正由什么组成

[English version](./model-harness-product.md)

刚开始比较 AI 产品时，我最自然关注的是模型。

哪个模型更强？哪个推理更好？哪个更会写代码？

但真的用 AI 做产品、做独立开发以后，我越来越觉得，这个判断方式不够了。

普通 Chat 当然也能理解代码，但 Coding Agent 可以进入 repo、修改文件、运行测试、读取结果，再继续下一步。设计类环境又可能给模型画布、组件和渲染结果，让它拥有普通聊天里没有的反馈。

差别不只是“谁更聪明”，还有模型周围的整个系统。

我现在会把一个 AI 产品粗略拆成三层：

**Model → Harness → Product**

- **Model** 提供基础的语言理解、推理和生成能力；
- **Harness** 把这些能力组织成可以完成工作的系统，包括 Context、Tools、Runtime、Permissions、执行循环和 Verification；
- **Product** 决定用户到底在完成什么任务、保留多少控制权，以及最终体验怎样成立。

这个拆法后来也改变了我判断 AI 产品的方式。

## 模型不是整个产品

一个强模型可以理解 Bug、提出修复方案，也可以解释架构。

但“知道应该怎么做”和“能在一个真实系统里把事情做完”，不是一回事。

例如我让 AI 修一个 Bug。

普通 Chat 可能只能看到我贴进去的代码、报错信息、上传的文件和当前对话。

Coding Agent 还可能看到：

- repo 结构和相关源代码；
- Git 状态和 diff；
- 项目规则；
- build 与测试结果；
- 自己前一步操作后产生的新状态。

很多软件问题根本不只存在于一个文件里。一个接口失败，原因可能在 schema、另一个 service、旧 migration，甚至最近一次其他模块的修改。

所以 Coding Agent 看起来“更懂项目”，当然可能有模型能力的原因，但也可能只是因为产品让模型更接近了真实工作现场。

同一个原则也适用于其他 AI 产品。

AI 不只是需要更多信息，它还需要知道哪些信息是现在有效的、哪些和当前任务有关、哪些值得相信。

一个真实 workspace 里可能同时有最新产品定义、过期需求、已放弃方向、临时文件，以及 AI 生成但从未确认过的笔记。全部暴露给模型，Context 是更多了，但 source of truth 未必更清楚。

所以真正的产品问题会变成：

**模型什么时候应该看到什么？如果信息冲突，哪一个来源优先？**

能访问，不等于 grounded。

## Tools 和执行循环决定 AI 到底能做到哪里

模型可以告诉我：

> 你应该运行一下测试。

拥有工具的 Agent 可以真的去跑。

在不同环境里，模型可能可以读取和修改文件、执行命令、查询数据库、调用 API、操作浏览器、查看日志，甚至创建 Pull Request。

一旦拥有这些 Tools，AI 就不只是生成答案，它开始有能力改变真实系统状态。

这马上带来一个产品上的区别：

AI 可以**建议退款**，和它可以**真的退款**，是两个完全不同的产品。

所以 PM 不能只问：

“模型能不能做到？”

还要继续问：

- 这项能力应该只是建议，还是可以执行？
- AI 可以读取哪些数据？
- 哪些动作可以自动完成？
- 哪些必须先让用户确认？
- 哪些能力根本不应该开放？

Tools 只是第一步。

下一层差别，是系统能不能看到动作发生后的结果，再决定下一步。

普通 Chat 的工作方式经常是：

**我问 → AI 回答 → 我执行 → 把结果带回来 → AI 再回答**

Agentic workflow 更接近：

**理解 → 执行 → 观察 → 判断 → 调整 → 再执行**

这个循环很重要，因为真实工作几乎不会第一次就完全正确。代码会测试失败，API 会 timeout，数据可能缺失，AI 输出也可能违反规则。

如果每出现一个新状态，都需要人重新把信息搬回 AI，整个执行循环还是由人在推动。

如果系统可以在明确范围内自己看到结果、继续处理，AI 才开始从“回答问题”走向“完成任务”。

但 autonomy 也会带来 retry、tool calls、成本和新的失败方式，所以一个好的执行循环一定需要 stopping rule，而不只是“可以一直继续”。

## Verification 和 Permissions 决定 autonomy 是否可信

AI 说“完成了”，并不能证明任务真的完成了。

这是我在和 Coding Agent 长时间协作时感受特别强的一点。

不同结论，需要不同证据：

- type check 只能证明类型检查通过；
- test 可以验证具体行为；
- 数据库查询可以确认真实数据状态；
- 页面渲染才能验证视觉结果；
- production check 才能确认线上行为。

一种验证方式不能替另一种结论背书。

所以 Verification 不只是最后的 QA，它本身也是 AI 工作环境的一部分。

一个可工作的系统应该能回答：

- 什么证据才算完成？
- 哪些检查应该自动运行？
- 哪些地方仍然没有验证？
- 用户能不能查看结果？
- 做错以后能不能恢复或回滚？

Permissions 也不是一个简单的安全开关。

我以前会觉得，如果已经明确告诉 Agent：

实现 → 测试 → commit → push → PR → merge → deploy → UAT

那它应该沿着这条任务链继续执行。

实际使用时，却至少有三层不同授权：

1. **Task authorization**：用户希望 AI 最终完成什么；
2. **System execution permission**：当前运行环境允许执行哪些具体动作；
3. **External identity & authorization**：GitHub、部署平台、数据库等外部服务是否认可当前身份，并允许这个账号操作。

这三层并不会自动合并。

我允许部署，不代表 runtime 已经允许访问网络；runtime 允许访问网络，也不代表外部平台一定接受当前凭据。

这也改变了我对 AI autonomy 的理解。

目标不应该是取消所有审批。

更合理的状态是：

**常规动作在已知边界内尽量顺畅，只有真的需要人判断时才升级给用户。**

## Harness 是很多产品决定真正落地的地方

“Harness Engineering”听起来确实很工程，具体怎么搭 runtime、permissions、tooling 和 checks，也通常应该由工程团队负责。

但当 AI 开始读取真实业务数据、调用工具、替用户采取行动以后，Harness 会越来越多地承载产品政策。

例如一个 AI 客服 Agent。

Eval 可能先定义：

- 不能编造订单状态；
- 必须遵守退款政策；
- 涉及账号安全时必须转人工；
- 没有权限时不能承诺补偿。

Harness 还要把其中一部分要求落实成真实工作条件：

- Agent 去哪里读取最新退款规则；
- 可以读取哪些账户字段；
- 可以直接退款，还是只能提出建议；
- 金额到什么程度必须审批；
- 回复发送前经过哪些检查；
- 转人工时把哪些已有 Context 一起交过去。

这些机制当然由工程实现。

但背后的决定——信息权限、行动权限、停止条件、人工审核、可接受风险——同样也是产品决定。

这也是我觉得 AI PM 会开始变得更“技术化”的地方。

PM 不需要自己搭 sandbox，但应该知道 sandbox 在保护什么，为什么。

## Harness 之上，仍然还有 Product

即使 Harness 做得很好，它也只让系统更有能力、更可靠、更可控。

它不会自动回答：

**用户到底应该经历怎样的产品？**

Product 还要决定：

- AI 在帮助用户完成什么任务；
- 什么信息应该展示；
- 哪些动作只是建议，哪些自动执行；
- 用户在哪里审核或修改；
- 不确定性怎样表达；
- 任务无法完成时发生什么；
- 最终控制权保留多少给用户。

两个产品就算用同一个模型、类似的 Tools，也可能因为控制、透明度和 workflow 的设计完全不同，而产生完全不同的体验。

所以现在我看一个 AI 产品，不会只问：

“它用了什么模型？”

我还会继续看：

- **它能看到什么？** 当前 Context 是否可信、最新？
- **它能做什么？** 只能给建议，还是可以真的修改真实系统？
- **它能不能形成执行循环？** 执行以后能否看到结果，并在边界内继续？
- **它怎样知道自己做对了？** 有真实状态、测试、引用、确定性检查、人工审核，还是只有一段听起来合理的答案？
- **边界在哪里？** 什么需要审批？什么绝对不能做？什么条件下必须停止 retry 或自动执行？
- **用户还控制什么？** 能不能查看依据、修改结果、拒绝动作、从失败中恢复，并知道系统发生了什么？

这些问题很多时候比只比较 benchmark，更接近一个 AI 产品实际能做什么。

## 最后

模型仍然非常重要。

它决定了理解、推理和生成能力的大部分上限。

但一个真正能工作的 AI 产品，不只是“一个模型外面套了一层 UI”。

更接近：

**Model + Context + Tools + Runtime + Execution Loop + Permissions + Verification + Product Design**

我现在会把中间很大一部分统称为 **Harness**：让模型获得合适的工作条件，同时约束它怎样行动的一整套系统。

这里真正想表达的，不是所有 AI PM 都需要成为 Harness Engineer。

而是：当 AI 从生成文字，继续走向读取真实 Context、使用 Tools、采取真实行动以后，产品判断也必须跟着超出“模型最后输出什么”。

我们还需要设计：AI 可以知道什么、可以做到哪里、什么时候必须停、怎样证明完成，以及什么时候把控制权交还给人。

很多 AI 产品真正的差异，就发生在这里。
