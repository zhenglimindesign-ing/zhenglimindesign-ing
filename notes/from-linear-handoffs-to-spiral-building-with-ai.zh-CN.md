# 从线性交接到螺旋式推进：一个人用 AI 做产品以后，我怎样重新理解产品流程

[English version](./from-linear-handoffs-to-spiral-building-with-ai.md)

开始独立开发以后，我最需要调整的东西之一，并不是学会某个新工具，而是重新理解产品开发到底应该怎样往前走。

以前在团队里，我熟悉的流程大致是：

**产品 → 设计 → 工程 → 测试 → 上线**

真实项目当然从来没有这么整齐，但交接点很重要。设计需要相对清楚的问题，工程需要相对稳定的需求和方案，测试也需要知道什么才算完成。

所以传统流程不只是为了让产品变好，它也在解决多人协作的问题：不同角色需要在某个时间点，对同一件事有差不多的理解。

一个人借助 AI 做产品以后，这个限制突然少了很多。

上午还在讨论需求，下午 Coding Agent 就可以做出来。看到真实结果不对，晚上又可以回来改需求、改流程，再继续实现。

刚开始我会觉得：这是不是流程不够完整？

后来我慢慢发现，它并不是“没有流程”。

只是流程更像一圈一圈往前，而不是角色之间的接力。

所以新的问题不再是：

> 怎么在开发开始以前，把所有事情都想清楚？

而是：

> 哪些东西必须现在想清楚，哪些问题看到真实产品以后再回答更合理，以及什么时候应该停下来，把这一轮学到的东西整理好再继续？

## AI 让“做出来”变得比“想明白”快很多

这是我觉得最关键的结构变化。

现在一个想法很快就可以变成真实页面或工作流。

但代码写完，不代表产品判断已经成熟。

页面能打开，不代表信息层级是对的。

流程能跑，不代表用户目标已经清楚。

功能能用，也不代表用户真的需要。

过去团队里的需求评审、设计评审、工程讨论和测试，本来会自然制造一些停顿。

一个人可以直接借助 AI 从想法走到实现以后，这些停顿会消失很多。

这当然提高了速度，但也带来一个新的风险：

**产品可能长得比判断成熟得更快。**

所以速度变快以后，反而需要重新设计检查点。

## 1. 越难改、出错代价越大的决定，越应该早点认真想

不是所有东西都适合边做边改。

有些决定一旦错了，后面会牵动很多地方。

这类问题我现在会更早、更认真确认，例如：

- 产品到底给谁用；
- 真正在解决什么核心问题；
- 当前阶段最重要的用户路径；
- 核心对象和重要数据关系；
- 明确不做什么；
- 安全、权限、合规等高风险边界。

这里的原则不是“开发前先写一份完美 PRD”，也不是所有架构都必须一开始定死。

更简单的是：

**一个决定越难撤回、错了以后影响范围越大，就越值得提前投入判断。**

AI 实现得快，不是这些地方可以随便一点的理由。

恰恰相反，方向错了以后，AI 可能会更快地把错误继续铺开。

## 2. 有些问题，本来就应该让真实产品来回答

另一类问题很难只靠文档想清楚。

例如：

- 结果页应该先显示结论还是依据；
- 一个操作用 modal 还是单独页面；
- 哪些内容默认展开；
- 某个功能到底值不值得有独立入口；
- AI 真实输出放进去以后，页面会不会太重。

这些事情可以在 PRD 里讨论很久。

但真实内容一放进去，答案有时候马上就清楚了。

原本觉得不多的信息可能一下变得很拥挤；纸面上很顺的流程，实际点一遍却很别扭；写在需求里看起来必要的功能，放进完整路径以后可能完全重复。

所以我现在不会强迫所有产品细节都在开发前得到“最终答案”。

如果一个判断高度依赖真实内容、真实状态或真实交互，我会更愿意先用一个合理假设做出来，再基于结果继续判断。

这不是“先做再想”。

而是把不同问题放到更适合它们被回答的时间。

## 3. 先走通一条真实路径，而不是一下铺开整个产品

AI-assisted development 很容易让项目横向铺开：

这个页面完成，再做另一个页面；然后加筛选、设置、通知、更多 secondary flow。

每天都像在推进，因为很多东西不断被完成。

我现在更愿意先跑通一条从头到尾的用户路径。

哪怕是一个简单产品，也可以先保证：

**开始 → 完成核心动作 → 看到结果 → 做判断 → 保存或继续**

一条完整路径会逼很多层同时碰在一起：

- 需求；
- 数据；
- UX；
- 系统状态；
- AI 输出；
- 异常处理；
- 技术结构。

很多问题在单独做某一个页面时根本看不到，只有整条路径真实跑起来以后才暴露。

目标不是“尽量少做页面”。

而是先让一个真正有意义的用户结果足够真实，好让下一轮判断有依据。

## 4. 过去自然存在的停顿没了，就要自己主动加回来

这是我后来很重视的一个习惯。

Coding Agent 很擅长继续往前。

一个任务完成，就可以给下一个。一个页面做好，就可以再补几个功能。

过去团队里的交接会自然让项目停下来看看。

一个人做以后，需要自己主动创造这种停顿。

每完成一轮，我至少会换几个角度看：

**产品**：这件东西真的值得存在吗？Scope 有没有在没人明确决定的情况下变大？

**用户**：第一次来的人知道自己在哪里、什么最重要、下一步做什么吗？

**设计**：信息层级清不清楚？类似操作是否一致？几个页面放在一起还像同一个产品吗？

**工程**：当前实现是在支撑下一步，还是已经开始堆临时结构和 patch？

**AI 质量**：如果产品里有 AI，输出够不够好、有没有依据、哪里需要人工审核、失败与成本是否合理？

目的不是重新制造一套繁琐流程。

而是把原来“因为多人协作所以存在的检查点”，换成“因为这一轮已经获得新信息，所以值得停下来重新判断”的检查点。

## 5. 设计不能等功能全部完成以后才第一次认真处理

这件事我自己踩过比较明显的坑。

最初我会觉得：功能先做出来，最后再统一处理设计。

但只要 Coding Agent 开始实现功能，它其实已经在替产品做 UX/UI 决定：

- 用户从哪里进入；
- 第一眼看到什么；
- 信息怎样分组；
- 用 modal、drawer 还是新页面；
- loading / empty / error 怎么处理；
- 完成以后去哪里。

如果这些没有提前定义，Agent 仍然必须选一个答案。

单看每一次都可能说得过去，几轮下来却很容易彼此不一致。

所以我现在更倾向于让设计分层进入。

**开发前：**先定体验骨架——用户目标、入口和出口、主流程、信息层级、关键状态、还没决定的问题。

**一条真实路径跑通后：**基于真实内容和交互认真 review，再建立值得复用的视觉和交互模式。

**后续迭代中：**出现新的复杂 workflow，或者现有页面开始明显漂移时，再让设计回来。

设计不需要在开发前全部完成。

但也不能等所有功能做完以后，才第一次认真介入。

## 6. 每一圈结束以后，都应该让产品少一点模糊

“螺旋式推进”也很容易被滥用成一句：

> 反正我们一直在迭代，所以什么都可以先临时。

这不是我想表达的。

一轮结束以后，已经变清楚的东西应该被留下来。

例如：

- 产品边界变了，就更新 Product Definition；
- 流程变了，就更新对应 Spec；
- 一个长期影响后续的取舍确定了，就记进 Decision Log；
- 已经失效的需求和放弃方向及时删除或归档；
- 重复出现的 UI 模式整理成 shared component；
- 临时代码开始影响后续，就及时处理；
- 一个失败已经值得防止复发，就补测试或验证机制。

真正有效的循环，不只是“又做了一轮”。

而是这一轮得到的新理解，可以继续被下一轮使用。

否则项目只是一直在动，人和 Agent 却不断重新猜过去到底决定过什么。

## 我现在怎么理解“螺旋”

我不觉得 AI 出现以后，产品开发就不需要提前思考。

也不觉得“实现很快”就意味着“先做了再说”。

我更愿意这样区分：

- **高风险、难撤回的问题**：早点确定；
- **高度依赖真实内容和使用的问题**：允许晚一点成熟；
- **开发过程**：不只是执行，也是获取产品证据的方式；
- **每一轮之后**：把已经变清楚的东西沉淀下来。

这样一来，产品、设计、工程、验证不再整齐地排成几个一次性完成的阶段，而是在不同轮次里不断回来。

但每一圈应该往前。

所以我现在越来越少用：

> 这周又做了多少功能？

来判断进展。

我更关心：

> 这一轮以后，产品有没有比上一轮少一点模糊？

AI 让“还没有全部想清楚，就先做出来看看”变得容易很多。

真正需要练习的，是区分哪些不确定性可以通过做出来继续学习，哪些不确定性会把整个产品带错方向，以及什么时候应该主动停下来，把新证据重新变成产品判断。
